# Proposed API surface

`GET /api/v1/health` reports API availability. `GET /api/v1/ready` pings MongoDB and returns 200 when connected or 503 with `DATABASE_UNAVAILABLE` when it cannot connect. `GET /api/v1/openapi.json` serves the OpenAPI document. The remaining routes are planned contracts for the phases in `PHASED-PROMPTS.md`. All public API paths are versioned under `/api/v1`. Responses use `{ data, meta, error }`; list metadata contains `nextCursor`. Errors have stable codes, safe messages, and an `x-request-id` response header. IDs in routes are validated, and tenant identity is derived from the session rather than supplied in request data.

Internal routes use a separate `/internal/jobs/*` and `/internal/cron/*` namespace. They require provider signatures or a secret and must be idempotent. Webhook routes verify provider signatures on the raw request body before enqueuing work.

## Common query behavior

- Lists accept `limit` (capped), `cursor`, `sort`, and module-specific filters. Default order is stable and indexed.
- Mutations that can be retried accept an idempotency key. Concurrent edits use version checks where needed.
- `404` is used where exposing the existence of another tenant's resource would leak data; `403` covers known resources in the active tenant when permission is missing.
- Shared Zod schemas define the request and response shapes before endpoints are implemented. OpenAPI is generated from those contracts in Phase 2.
